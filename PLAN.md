# План реализации ChatList

Поэтапный порядок действий по реализации программы на основании [PROJECT.md](PROJECT.md).

---

## Этап 0. Подготовка проекта

1. Обновить `requirements.txt`: добавить зависимости для HTTP (`httpx` или `requests`), работы с `.env` (`python-dotenv`), при необходимости — типизации и тестов.
2. Создать структуру модулей:
   - `db.py` — доступ к SQLite
   - `models.py` — логика работы с нейросетями (CRUD, активация)
   - `network.py` — отправка запросов к API
   - `main.py` — GUI и связывание слоёв
3. Добавить файл `.env.example` с шаблоном переменных окружения для API-ключей.
4. Обновить `.gitignore`: исключить `.env`, файл БД (`chatlist.db` или аналог), `__pycache__`.

---

## Этап 1. База данных (`db.py`)

1. Реализовать инициализацию SQLite: создание файла БД, применение схемы из [DATABASE.md](DATABASE.md).
2. Реализовать функции для таблицы **prompts**:
   - добавление промта (дата, текст, теги);
   - получение списка промтов;
   - поиск и сортировка (опционально).
3. Реализовать функции для таблицы **models**:
   - CRUD для моделей (name, api_url, api_id, is_active);
   - получение активных моделей (`is_active = 1`).
4. Реализовать функции для таблицы **results**:
   - сохранение выбранных результатов;
   - чтение сохранённых результатов;
   - поиск и сортировка (опционально).
5. Реализовать функции для таблицы **settings**:
   - чтение/запись настроек по ключу.
6. Инкапсулировать всё в `db.py`: внешний код не обращается к SQLite напрямую.

---

## Этап 2. Конфигурация и API-ключи

1. Загрузка переменных окружения из `.env` через `python-dotenv`.
2. В таблице `models` хранить **имя переменной** (например, `OPENAI_API_KEY`), а не сам ключ.
3. При отправке запроса: по `api_id` модели читать ключ из окружения; если ключ отсутствует — возвращать понятную ошибку в интерфейс.

---

## Этап 3. Логика моделей (`models.py`)

1. Описать структуру данных модели (dataclass или TypedDict): id, name, api_url, api_id, is_active.
2. Реализовать обёртки над `db.py`:
   - список всех моделей;
   - список активных моделей;
   - добавление, редактирование, удаление, переключение `is_active`.
3. Валидация полей при сохранении (непустое имя, корректный URL, уникальность имени).

---

## Этап 4. Сетевой слой (`network.py`)

1. Реализовать базовый интерфейс отправки промта в API (единая сигнатура: url, ключ, промт → текст ответа или ошибка).
2. Добавить адаптеры под разные типы API (опционально, по мере необходимости):
   - OpenAI-совместимый формат (OpenAI, DeepSeek, Groq и т.д.);
   - при необходимости — отдельные обработчики для иных форматов.
3. Реализовать параллельную или последовательную отправку промта во все активные модели.
4. Обработка таймаутов, HTTP-ошибок и невалидных ответов — возвращать текст ошибки вместо ответа модели.
5. Логирование запросов (опционально): запись в файл или таблицу.

---

## Этап 5. Временная таблица результатов (в памяти)

1. Описать структуру строки временной таблицы: model_name, model_id, response_text, selected (bool).
2. Хранить список в памяти (в главном окне или отдельном классе-сервисе).
3. Правила жизненного цикла:
   - при новом промте — очистить временную таблицу;
   - после получения ответов — заполнить заново;
   - после «Сохранить» — записать выбранные строки в `results`, очистить временную таблицу.

---

## Этап 6. Графический интерфейс (`main.py`)

### 6.1. Главное окно — общая компоновка

1. Верхняя область: поле ввода промта, кнопка «Отправить», выпадающий список сохранённых промтов.
2. Центральная область: таблица результатов (модель | ответ | чекбокс).
3. Нижняя панель: кнопки «Сохранить», «Новый запрос» (при необходимости).
4. Меню или вкладки для управления моделями, просмотра сохранённых результатов, настроек.

### 6.2. Рабочий процесс (по PROJECT.md)

1. **Ввод промта** — пользователь вводит текст или выбирает из `prompts`; при выборе — подставить текст в поле ввода.
2. **Отправка** — взять активные модели, вызвать `network.py`, заполнить временную таблицу, отобразить в GUI (с индикатором загрузки).
3. **Просмотр результатов** — таблица с чекбоксами; возможность выделить все / снять все.
4. **Сохранение** — строки с `selected = True` → `db.save_results(...)`, очистка временной таблицы, уведомление пользователю.
5. **Новый запрос** — очистка поля и временной таблицы.

### 6.3. Дополнительные экраны

1. **Управление моделями** — таблица моделей, форма добавления/редактирования, переключатель `is_active`.
2. **История промтов** — просмотр, поиск, сортировка по дате/тегам.
3. **Сохранённые результаты** — просмотр таблицы `results`, поиск, сортировка.
4. **Настройки** — редактирование записей из таблицы `settings`.

## Этап 7. Связывание слоёв и обработка ошибок

1. Подключить сигналы PyQt к обработчикам: отправка в фоновом потоке (`QThread` / `QRunnable`), чтобы GUI не зависал.
2. Единообразные сообщения об ошибках (`QMessageBox`).
3. При первом запуске — автоматическая инициализация БД и (опционально) seed-данные с примерами моделей.

## Этап 8. Опциональные функции

1. Поиск и сортировка во всех таблицах GUI.
2. Экспорт выбранных результатов в Markdown / JSON.
3. Расширение списка поддерживаемых провайдеров API.
4. Логи запросов (файл `logs/` или отдельная таблица).

## Этап 9. AI-ассистент для улучшения промтов

Реализация функции из [PROJECT.md](PROJECT.md), §7. Зависит от готовых модулей `network.py`, `models.py`, `db.py` и вкладки «Запрос» в `main.py`.

### 9.1. Цель и границы

**Вход:** исходный текст промта из поля ввода на вкладке «Запрос».

**Выход для пользователя:**
- одна улучшенная версия промта;
- 2–3 альтернативные переформулировки;
- при необходимости — адаптации под тип задачи (код, анализ, креатив).

**Ограничения:**
- запрос уходит **в одну** выбранную модель через существующий OpenRouter-клиент (`network.send_to_model` / `send_openai_compatible`);
- ассистент не сохраняет результат в БД автоматически — только подставляет текст в поле ввода по действию пользователя;
- асинхронность через `QThread`, по аналогии с `SendWorker`.

### 9.2. Модуль `prompt_assistant.py` (новый файл)

1. Описать dataclass результата, например `PromptImprovementResult`:
   - `original: str` — исходный промт (эхо для UI);
   - `improved: str` — основная улучшенная версия;
   - `alternatives: list[str]` — 2–3 варианта (допускать меньше при частичном ответе модели);
   - `adaptations: dict[str, str]` — ключи вроде `code`, `analysis`, `creative` → текст адаптации (пустой словарь, если модель не вернула блок).
2. Константа или функция `_build_meta_prompt(user_prompt: str) -> str`:
   - системная инструкция: улучшить ясность, структуру, конкретность;
   - попросить ответ **строго в JSON** с полями `improved`, `alternatives` (массив строк), `adaptations` (объект строк);
   - язык улучшенного промта — тот же, что у пользователя (или явно указать в meta-prompt).
3. Функция `improve_prompt(text: str, model: models.Model) -> PromptImprovementResult | str`:
   - собрать meta-prompt + исходный текст;
   - вызвать `network.send_to_model(model, meta_prompt)`;
   - если `response.error` — вернуть строку ошибки для GUI;
   - распарсить JSON из ответа (`json.loads`, вырезка из markdown-блока `` ```json `` при необходимости);
   - при ошибке парсинга — fallback: весь текст ответа положить в `improved`, `alternatives` пустой (с предупреждением в UI).
4. Не дублировать HTTP-логику — только orchestration поверх `network.py`.

### 9.3. Настройки (таблица `settings`)

1. Добавить ключ **`prompt_assistant_model_id`** — ID записи из таблицы `models`, через которую работает ассистент.
2. В `seed.py`: при первом запуске, если ключ пуст — подставить ID первой активной модели (например `openai/gpt-4o-mini` из seed-данных).
3. Расширить **`SettingsTab`** в `main.py`:
   - выпадающий список «Модель для улучшения промта» — все модели из `models.list_models()` (не только активные: ассистент может использовать отдельную модель);
   - сохранение/загрузка через `db.get_setting` / `db.set_setting`;
   - при отсутствии модели в БД — показать предупреждение.
4. Вспомогательная функция в `models.py` (опционально): `get_prompt_assistant_model() -> Model | None` — читает setting, возвращает модель или `None`.

### 9.4. Фоновый поток (GUI, `main.py`)

1. Класс **`ImprovePromptWorker(QThread)`** по образцу `SendWorker`:
   - вход: `prompt_text: str`, `model: models.Model`;
   - в `run()` вызывает `prompt_assistant.improve_prompt`;
   - сигналы: `finished_ok(PromptImprovementResult)`, `finished_error(str)`.
2. Блокировка UI на время запроса:
   - отключить кнопку «Улучшить промт» и «Отправить»;
   - `status_label`: «Улучшение промта…»;
   - по завершении — восстановить состояние.

### 9.5. Диалог результатов

1. Класс **`PromptImproveDialog(QDialog)`**:
   - заголовок: «Улучшение промта»;
   - секция **«Исходный»** — read-only `QTextEdit`;
   - секция **«Улучшенный»** — read-only + кнопка **«Подставить»**;
   - секция **«Альтернативы»** — список или вкладки с 2–3 вариантами, у каждого кнопка «Подставить»;
   - секция **«Адаптации»** (сворачиваемая / `QGroupBox`) — три блока: «Код», «Анализ», «Креатив», у каждого «Подставить»;
   - кнопка «Закрыть».
2. Обработчик «Подставить»:
   - `prompt_edit.setPlainText(выбранный_текст)`;
   - сброс `session.prompt_id = None` (текст изменился относительно сохранённого промта);
   - опционально закрыть диалог или оставить открытым для сравнения вариантов.
3. Если парсинг ответа был частичным — `QLabel` с предупреждением «Ответ модели распознан не полностью».

### 9.6. Интеграция во вкладку «Запрос» (`RequestTab`)

1. Рядом с кнопкой «Отправить» добавить кнопку **«Улучшить промт»** (горизонтальный layout: `[Улучшить промт] [Отправить]`).
2. Обработчик `_on_improve_prompt`:
   - проверить непустой текст в `prompt_edit` — иначе `QMessageBox.warning`;
   - получить модель ассистента из settings; если `None` — сообщение «Выберите модель в настройках»;
   - проверить API-ключ через `config.get_api_key` — та же логика, что при отправке;
   - запустить `ImprovePromptWorker`;
   - по `finished_ok` — открыть `PromptImproveDialog`;
   - по `finished_error` — `QMessageBox.critical`.
3. Не очищать временную таблицу результатов при улучшении — это отдельное действие от «Отправить».

### 9.7. Обработка ошибок и краевые случаи

| Ситуация | Поведение |
|-----------|-----------|
| Пустой промт | Предупреждение, запрос не отправляется |
| Не выбрана модель ассистента | Сообщение + переход в настройки (подсказка) |
| Нет API-ключа | Текст из `config.missing_api_key_message` |
| Таймаут / HTTP-ошибка | Показать текст ошибки из `network` |
| Невалидный JSON от модели | Fallback: показать сырой ответ как «улучшенный» |
| Модель вернула &lt; 2 альтернатив | Показать сколько есть; не падать |
| Пользователь закрыл диалог без подстановки | Без изменений в поле ввода |

### 9.9. Тестирование

1. **Happy path:** промт «объясни python» → улучшенный + альтернативы + адаптации → «Подставить» → текст в поле изменился.
2. **Пустой промт** — предупреждение.
3. **Без ключа в `.env`** — понятная ошибка.
4. **Модель вернула prose вместо JSON** — fallback, диалог не падает.
5. **Смена модели в настройках** — следующий запрос идёт в новую модель.
6. **Длинный промт** — диалог с прокруткой, без зависания GUI (worker в фоне).
